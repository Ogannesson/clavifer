# AGENTS.md — Clavifer

A personal credential service for AI agents. The agent calls an upstream API through a _connection_ and the server adds the credential, so the agent never holds it; what each agent installation may do is decided by the Owner in a web console. Cloudflare Worker + D1 + R2 (Hono, Better Auth 1.7.4, oauth-provider, drizzle), a Go CLI `clavifer` that bridges MCP hosts to the server, and a React web console.

## Start here

- **Asked to deploy this for someone?** Follow `docs/deploy.md`. Its first section says where to start: a deployment to Cloudflare begins at Part B, and Part A is an optional local trial. It is written to be executed by an agent: every step says who performs it (you or the human), the exact command, how to verify the result and whether the step can be run again. Do the steps in order. When a step fails, do what the document says for that failure; do not improvise around it.
- **Asked to connect an agent host (Claude Code, Codex) to an existing deployment?** Follow `docs/clients.md`.
- **Asked to use a deployment** (call an API through it, request access)? The server's MCP instructions and `integrations/skills/clavifer/SKILL.md` cover that. Nothing else in this file is needed.
- **Changing the code?** Read the rest of this file.

One rule holds in every case: **secret values never pass through you.** That covers the credentials stored in the service, the Worker secret `ROOT_KEY`, the bootstrap token, `.dev.vars` and everything under `work/`. The scripts write these to files and print only the path. Do not open, print, copy or summarize those files, and do not write a secret's value into a command, a commit, a log or the conversation. A command may refer to an environment variable by name and let the shell expand it. The human enters credential values in the console.

## Layout

- `apps/worker/src/` the Worker: `index.ts` routes and middleware, `context.ts` authentication / audit / request context, `vault.ts` resources and the proxy, `mcp.ts` MCP tools, `setup.ts` the bootstrap token, creating the Owner and resetting its password, `backup.ts` the automatic backup and R2 retention, `export.ts` the snapshot both backups are made of and the full export, `import.ts` importing a snapshot, `archive.ts` sealing of old audit rows and access requests into `archive/`.
- `apps/web/` the React web console. Its interface is in Chinese only.
- `packages/core/` encryption, the proxy's path / header boundary, and `snapshot.ts`, the snapshot format; `packages/auth/` Better Auth plugin configuration and schema; `packages/contracts/openapi.json` is generated by `npm run openapi:generate`.
- `cmd/clavifer/` the Go CLI (Windows first; `lock_*.go` and `archive_*.go` are per-platform).
- `integrations/skills/clavifer/` the Skill shipped with each version; `integrations/adapters/` install scripts (the Skill, the CLI's stable path).
- `migrations/` append only, never edited; `docs/` user documentation; `scripts/` local development, test and build scripts.
- `wrangler.jsonc` is a template: its `account_id` is all zeros, so wrangler run against it reaches no account, and its hostnames and database IDs are placeholders that `docs/deploy.md` has you replace.

```
npm run format:check

gofmt -l cmd/           # must print nothing
go vet ./... && go test ./...
npm run test:e2e        # isolated miniflare database + the Go bridge, no external services
npm run test:system     # Windows only: the real credential store; writes synthetic entries and removes them
```

`npm run test:hosts` additionally starts the Codex and Claude Code installed on this machine and checks that they discover the MCP tools. It does not call a model.

## Conventions

- The security boundary is on the server. Grants decide what an installation may do; OAuth scopes are not a boundary. `secret:read` can be granted for a subset of fields. Revocation works because every request checks `oauthClient.disabled`.
- Adding a grant, approving a request, issuing an authorization code, saving a connection, the full export (a GET) and changing the backup recipient require a sign-in within the last 10 minutes (`recentLoginRequired` in `index.ts`, and the `/api/auth/*` handler for authorization codes). Every other admin write needs only an Owner session and the same origin. `oauth_query` is accepted only with sign-in, consent and continue.
- Every decision about a connection request is made in `invoke()` in `vault.ts`, in this order:
  1. Deny rules. This is the only absolute refusal (`path_denied`, which names the rule that matched).
  2. Rules that require a one-time approval.
  3. Inside the regular scope (allowed paths + methods): a free rule or a timed grant lets the request through. Outside it: only a live scope extension on the grant does.
  4. A one-time approval lets a request through inside or outside the regular scope.

  The error codes `path_not_allowed`, `method_not_allowed`, `approval_required` and `grant_required` each carry a hint for the next step. Submitting a request for one-time approval checks only the input, that the connection exists, and the deny rules.

- Scope extensions are stored in `grants.extensions_json`, each with its own expiry and always both `paths` and `methods`, non-empty (the v1 snapshot requires them; the migration's comment calling them optional is wrong). Approving a request merges them (union); a grant made directly by the Owner replaces them; revoking the grant ends them.
- Rule syntax and matching are in `packages/core/proxy.ts` (`parseRule` / `matchRule`). Only ASCII is lowercased; GET covers HEAD. A path may contain `%2F` and encoded spaces, and all matching uses the decoded path (decoding splits segments, it never joins them).
- A one-time approval is bound to a fingerprint of the request that includes the raw path, is consumed once within 10 minutes, and works only over MCP: the REST client adds request headers of its own and cannot resend a request unchanged.
- `credentials.list` lists every connection, with its description, but only the secrets granted to the caller.
- Other origins. Where a credential may go besides the connection's fixed origin is set by `hosts` (extra hosts: an exact name or `*.suffix`) and `anyHost` (any address, off by default) in the connection's policy. Only the Owner can change either, in the console; a setup draft may carry `hosts` but not `anyHost`, and an update draft may change neither.
  - `origin` on `requested.invocation` and on `http.request` sends that one request to another address using the connection's way of adding the credential.
  - Whether the host is listed is checked at submission and again at execution (`host_not_allowed`).
  - Only a one-time approval counts. Free rules, timed grants and scope extensions do not; deny rules apply as usual.
  - The request fingerprint includes the normalized origin, so an approval for A cannot be sent to B or to the fixed origin.
  - The approve request must echo the origin (`origin_mismatch`), so a page that was not refreshed cannot approve.
  - Host matching is `validHost` / `matchHost` in `packages/core/proxy.ts`. It compares only the hostname after URL normalization and ignores the port.
  - The checkbox on the red warning card is a step in the console only. The REST proxy does not support `origin`. The actual address is not written to the audit table; find it in the request that `access:consume` points to, which after 25 hours may already be sealed in an `archive/` segment.
- Drafts. `requested.setup` and `requested.update` on `access.request` propose configuration for the Owner to approve.
  - `setup`: a new secret given only as field names, plus 1–20 `connections` that use it. It cannot refer to an existing secret. This is how an upstream spread over several hosts is created in one go.
  - `update`: changes only a connection's name, description, paths, methods and its three kinds of rules. It cannot change the origin or the authentication.
  - Both carry a table of tests (for `setup`, one per connection). On submission the tests are run with the pure function `decide()` in `vault.ts`, the same one `invoke()` uses; a mismatch returns `tests_failed`.
  - The IDs of the new secret and connections are generated at submission and stored in `requested_json.ids` (`secretId`, and `connectionIds` in the order of `connections`). On approval the secret (the Owner enters its values), all connections and the request status are written in one batch.
  - `update` records the connection's `updated_at`; if it has changed by the time of approval the result is `connection_changed`.
  - Drafts never carry grants.
  - Submission checks only connection names (`name_taken`). Secret names are checked at approval (`secret_name_taken`), so that an installation cannot probe for the names of secrets it cannot see.
  - A request takes at most 256 KiB as stored, counted on `requested_json` and `reason` after JSON escaping (`request_too_large`). An installation may have at most 20 pending requests and 1 MiB of them as stored (`too_many_pending`); revoking the installation denies them all.
- The REST proxy streams responses through with no size limit (the 20-second timeout cuts long streams). MCP `http.request` is limited to 1 MiB of text. There is no detection of an upstream echoing a credential back: configure trusted upstreams only.
- MCP has one endpoint, `/v1/mcp`, and the audience is always `${APP_ORIGIN}/v1`. Dynamic client registration is off: installations are created only by the Owner in the console.
- Every response carries `nosniff`, `no-referrer` and a content security policy. The policy for pages allows only the service's own scripts and styles, nothing inline. Edge features that inject third-party scripts into pages (such as the automatic setup of Cloudflare Web Analytics) are blocked by it and must be turned off for the service's hostname.
- An audit row's `request_id` equals the `x-request-id` response header.
- `audit_events.created_at` and `access_requests.created_at` are always `now()` at the INSERT, never back-filled: sealing (`archive.ts`) moves rows past a fixed age into immutable segments by `(created_at, id)` range, and a row dated before a sealed range makes every later snapshot fail to import (`tests/archive.test.ts` lists the statements that may write these tables). The one exception is the import (`import.ts`): it writes a snapshot's rows with the `created_at` they had, into an instance it emptied, together with the segments they came with, and its commit refuses any row dated at or before the last segment of its kind.
- The MCP configuration of a host (Codex, Claude Code) points to the installed copy of the CLI, which `integrations/adapters/install-cli.ps1` updates. `dist/` holds build output only: `npm run build:cli` does not change the installed copy.
- The additional authenticated data of an encrypted secret, `["clavifer", 1, ownerId, secretId, version]`, and of the archive identity, `["clavifer", 1, ownerId, "archive-identity"]` (`packages/core/crypto.ts`), are written into stored data: changing either makes the stored ciphertext undecryptable. To replace one, add a new version and keep accepting the old value.
- The snapshot format `clavifer-backup-v1` is specified by the header comment of `packages/core/snapshot.ts`, and its zod schemas are the only definition of its records. v1 is frozen: never change what it means; a change is a v2 with a conversion. The samples in `tests/fixtures/v1/` are never modified once released (`tests/fixtures/v1/README.md`).
- The automatic backup and the full export are one snapshot (`snapshot()` in `export.ts`): every table it carries and the segment manifest read in one D1 batch, every record checked against the schemas, and the whole refused when the instance is inconsistent (`checkReferences`; the console shows it, and the last good backup stays). The automatic backup names each sealed segment by its key in the same bucket; the full export embeds the segment files, after a `head()` found each with the SHA-256 its manifest row recorded.
- The full export (`GET /admin/backup/export`) runs only for `Sec-Fetch-Site: same-origin`, since its recipient is in the link, and counts as whole only once it has written a `backup:export` audit row with result `complete` under the console's export id, after the last byte.
- The automatic backup runs when `backup_state.revision` moved (or once a day). Triggers in the migration move it on every change to what a snapshot carries, but not on a delete other than a Passkey's (sealing deletes in the batch that inserts its manifest row), a Passkey's counter (every sign-in) or an audit row of the actor `system` (the backup's and sealing's own). D1 counts the rows a trigger writes in `meta.changes`, so a statement on a table with a trigger is checked against 0, never against 1. Better Auth's atomic fallback (`consumeOne`, `incrementOne` in `@better-auth/core`) throws unless a write reports 0 or 1 changes, so `verification`, `deviceCode`, `oauthRefreshToken` and `rateLimit` never get a trigger.
- Importing a snapshot (`import.ts`, the console's `/setup`) is the other way to initialize an instance, for a migration and a disaster recovery alike. The browser decrypts the file and sends it in three steps. The start spends the setup token like creating the Owner does (`clearOut` included) and records the import as `system_state.import_id` (`{id, owner, header}`); the id is a bearer credential that travels only in bodies. Every later batch starts with an import guard of the `tokenGuard` kind that fails the whole batch unless that id is still the one recorded and the instance still uninitialized. Chunks write records with their seq in `import_chunks` (a chunk sent again is written once), credential versions re-encrypted under this instance's root key; an embedded segment goes to a new key, a referenced one must be in the bucket with its checksum or be skipped by the Owner. The chunk route refuses before reading its body when no import is in progress. The commit checks counts, references and segment order, then writes the Owner, its Passkeys only on the hostname of the snapshot, and the instance's state in one batch whose guard also requires the number of chunks it checked, and which spends any token issued meanwhile. Only structure and references are checked, never this version's business rules: a version that tightens a rule converts stored and imported rows alike.
- The service reads its one secret, `ROOT_KEY`, only from Worker Secrets (from `.dev.vars` locally); it is never in the repository or the database. The deploy entry `scripts/deploy.mjs` (`npm run deploy -- --env <name>`, or `--local` for `.dev.vars`) generates it in its own process, hands it to `wrangler secret put` on stdin and never writes or prints it; it does so only for a Worker without `ROOT_KEY` whose database is uninitialized, or for `--rebuild`. No copy exists anywhere else: a lost or overwritten key is recovered with `--rebuild` into a new database and an import of the latest automatic backup.
- Every deployment goes through the deploy entry. It parses the chosen environment's configuration once per run with wrangler's `unstable_readConfig` (the other environments only to check that no two share a Worker, database, bucket or hostname), refuses placeholders and inconsistent configurations, compares the live Worker, hostname and database with them before writing anything, and passes `--config` and `--env` to every wrangler call. A check that a configuration is deployable belongs there, not in `build.command`.
- Setup and recovery (`apps/worker/src/setup.ts`, the console's `/setup`) take a one-time token whose SHA-256 the deployment writes into `system_state` as `bootstrap_token` (`scripts/bootstrap-token.mjs`); the token travels only in the `x-bootstrap-token` header. It lasts 24 hours on an uninitialized instance, where it creates the Owner, and 1 hour on an initialized one, where it sets a new password and removes the Owner's Passkeys and sessions. It is spent by the first statement of the batch that does the work (`tokenGuard`, which fails the whole batch on a wrong, expired or spent token or the wrong instance state). Creating the Owner empties every table first (`clearOut`; a new table goes in its list) and stores the archive identity encrypted in `system_state` as `archive_identity`. `clearOut` also writes the one `oauthResource` row the OAuth provider would seed for `${APP_ORIGIN}/v1`: left to the provider, concurrent first requests each insert it, and the provider misses the duplicate-key error drizzle wraps, so one of them fails. Better Auth's sign-up and its `oauth2/create-client`, `update-client` and `delete-client` are closed: `/admin/clients` is the only writer of installations.
- `ROOT_KEY` is a ring of `<id>:<32 bytes base64url>`, current first, parsed only by `parseRootKeys` in `packages/core/crypto.ts`; the key that wraps secrets and the Better Auth secret are derived from it with HKDF. Creating the Owner records the fingerprint of every key in `system_state.root_key_fingerprints`, and a Worker whose ring does not match them answers `503 root_key_mismatch` everywhere but `/healthz` and skips its scheduled work (`keyState` in `context.ts`). On an initialized instance a `ROOT_KEY` that cannot be parsed makes every route, `/healthz` included, answer `503 invalid_root_key`; an uninitialized one fails only where the key is used. `npm run deploy -- --rebuild` replaces the key only after `/healthz` says it is lost (`keys: "mismatch"` or `invalid_root_key`) or `wrangler d1 info` reports every database the deployed versions are bound to as not found (a deleted database: the import re-encrypts under the new key), never on any other answer.
- Trade-offs: add nothing that is not needed; validate only what can change between runs; no defensive fallbacks. When behavior changes, update the matching sentences in `README.md` and `docs/`; do not add new long documents.

## Deploying a change

When a staging environment exists, deploy to it and verify there first, then to production. The commands are in the [Upgrading](docs/deploy.md#upgrading) section of `docs/deploy.md`.

A deployment can keep notes about itself (its hostnames, accounts and procedures) in `private/AGENTS.md`, which is not part of this repository. If the checkout contains that file, read it as well.
