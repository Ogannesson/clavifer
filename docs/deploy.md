# Deploying Clavifer

This document is written to be executed by a coding agent on behalf of a person. The person says "deploy this by following docs/deploy.md"; the agent runs the commands and stops wherever a step belongs to the human. A person deploying by hand follows the same steps and performs the Agent steps too.

The document has two parts, and where to start depends on what was asked:

- Asked to deploy to Cloudflare: read the sections before Part A, then start at [Part B](#part-b-production-deployment). Do not perform Part A.
- Asked to try Clavifer locally, or the human wants to look at it before deciding: read the sections before Part A, then perform [Part A](#part-a-local-trial). It is optional and needs no Cloudflare account.
- Asked to try it first and deploy if the trial goes well: read the sections before Part A and perform Part A. When it is finished, ask the human whether to continue with the deployment. If the human agrees, start at Part B.
- If it is not clear which of these was asked, ask the human.

Cloudflare Workers with D1 and R2, on the Workers Paid plan, is the only supported platform.

The agent must run on the human's own machine: the human opens files in the checkout and, in Part A, browses to `localhost`.

## Conventions

- Every step has a `Who` line that names who performs it. `Agent` is the coding agent executing this document. `Human` is the person who owns the Cloudflare account and becomes the Owner, the single administrator of the service.
- In a Human step, the agent sends the quoted message, waits for the reply, and then runs the check under `Verify`. The agent does not perform a Human step itself.
- `Verify` states what to run and what counts as success. `Rerun` states whether the step can be repeated. `If it fails` lists the failures the maintainer has met or looked up. Any failure that is not listed falls under [Stop and ask the human](#stop-and-ask-the-human).
- Run every command from the repository root.
- A command shown once is the same in PowerShell 7 and in POSIX shells. Where the two differ, both are given.
- `curl` means the curl program. In Windows PowerShell 5.1 (`$PSVersionTable.PSVersion.Major` prints `5`), type `curl.exe` instead.
- Every `curl` request to the local instance carries `--noproxy localhost`. When `HTTP_PROXY` is set, curl sends requests for `localhost` to the proxy too, and the proxy can answer with success while the service is not running.
- An existence check is used throughout. To learn whether a file exists without reading it, run `Test-Path <path>` in PowerShell, or `test -e <path> && echo True || echo False` in a POSIX shell. Both print `True` or `False`.
- The deploy entry, `npm run deploy`, is the only way this document puts code, keys or migrations on Cloudflare or into the local instance. It stops with a line that starts with `deploy: ` when it refuses or fails; npm then adds `npm error` lines of its own, and the exit status is 1. The `deploy: ` line is the one that names the cause. Its paths are printed with the separator of the operating system: `work\production-bootstrap.token` on Windows where this document writes `work/production-bootstrap.token`.
- wrangler does not wait for input when it has no terminal. It answers its own questions and prints `🤖 Using fallback value in non-interactive context`. These lines are expected.
- A wrangler command with `--json` prints pure JSON on standard output. Its other lines go to standard error: a warning about proxy environment variables when such variables are set, and the `npm notice` lines that `npx` adds. Read the JSON from standard output only and do not merge the two streams; merged, the warning line `[WARNING]` comes before the JSON and itself starts with `[`. Commands without `--json` start with a banner that can mention a newer wrangler. All of this is expected.
- Where a step tells a failure by the exit status, it means any non-zero status. On Windows, wrangler can exit with 127 instead of 1 after it has printed an API error.
- The web console, the Owner's management site, is in Chinese only. This document quotes each label as it appears in the console, followed by its meaning in parentheses.

## Secrets never pass through the agent

Clavifer exists so that agents work without seeing credentials. The deployment follows the same rule.

The agent must not open, print, copy, summarize or quote any of these, and must not write a value taken from them into a command:

- `.dev.vars`
- every file under `work/`
- `clavifer-backup-key.txt`, the private key file the console downloads, and any other age private key file
- everything under `.wrangler/`, which holds the local database with sessions and password hashes
- the value of the environment variable `CLOUDFLARE_API_TOKEN`

The agent may run an existence check on these files, and may pass their paths to the commands in this document. The Worker's one secret, `ROOT_KEY`, is generated by the deploy entry and handed to wrangler on standard input; it is never written to a file or printed, and no copy of it exists. In Part A the deploy entry writes the local key to `.dev.vars`. The bootstrap token goes to a file under `work/`, and the deploy entry prints only its path.

What is forbidden is the value: writing it into a command, printing it, or reading it. Referring to the token by the name of its variable is allowed. In `$env:CLOUDFLARE_API_TOKEN` (PowerShell) or `$CLOUDFLARE_API_TOKEN` (POSIX), the shell fills in the value when the command runs, and the value does not enter the conversation. Step 2.7 uses the token this way.

Do not run a command that prints the whole environment (`env`, `printenv`, `Get-ChildItem Env:`), because the output would include the API token. To learn whether a variable is set, run `[bool]$env:CLOUDFLARE_API_TOKEN` in PowerShell, or `test -n "$CLOUDFLARE_API_TOKEN" && echo True || echo False` in a POSIX shell.

When `npm run dev` starts, wrangler tells an agent about a local data interface under the path `/cdn-cgi/local/explorer`. It reads the local database. Do not call it.

The human never pastes a secret into the conversation. If a secret value appears in command output anyway, stop and tell the human which one.

## Stop and ask the human

Stop, report what you found, and wait for a decision in each of these cases:

1. A step would cost money: enabling R2, changing the Workers plan, buying a domain.
2. A step would delete or overwrite data. This includes a D1 database, an R2 bucket or a Worker that already exists under a name this document uses, and an existing `.dev.vars`. The deploy entry replaces the bootstrap token file by itself; that is expected.
3. The deploy entry refuses the hostname because it resolves already or another Worker serves it (Step 2.6).
4. Anything about key material that a step does not spell out: running the deploy entry with `--rebuild` outside [Recovering from a lost root key](#recovering-from-a-lost-root-key), setting or deleting `ROOT_KEY` by hand, deleting or moving a key file.
5. A command's result differs from what `Verify` describes, and no `If it fails` entry covers it.

## Names and placeholders

These names are fixed by `wrangler.jsonc`. Part B uses the `production` column. The `staging` column belongs to the optional second environment described under [Staging environment](#staging-environment).

| Thing                    | `production`                      | `staging`                         |
| ------------------------ | --------------------------------- | --------------------------------- |
| wrangler environment     | `production`                      | `staging`                         |
| Worker                   | `clavifer-production`             | `clavifer-staging`                |
| D1 database              | `clavifer`                        | `clavifer-staging`                |
| R2 bucket                | `clavifer-backups`                | `clavifer-staging-backups`        |
| Hostname in the template | `credentials.example.com`         | `credentials-staging.example.com` |
| Bootstrap token file     | `work/production-bootstrap.token` | `work/staging-bootstrap.token`    |

Replace each placeholder below with its value before running a command.

| Placeholder     | What it is                                                            | Where it comes from                                                 | Used in               |
| --------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------- |
| `<HOSTNAME>`    | The hostname that serves the service, such as `vault.example.org`     | The human, Step 1.4                                                 | Steps 2.5 to 2.7, 3.1 |
| `<ZONE_ID>`     | The ID of the Cloudflare zone that contains `<HOSTNAME>`              | The human, Step 1.4                                                 | Step 2.7              |
| `<ACCOUNT_ID>`  | The ID of the Cloudflare account to deploy into                       | Step 2.1, confirmed by the human                                    | Step 2.2              |
| `<DATABASE_ID>` | The `uuid` of the D1 database `clavifer`                              | The output of `d1 list --json`, Step 2.3                            | Step 2.5              |
| `<RULESET_ID>`  | The ID of the zone's configuration ruleset                            | The output of the list request, Step 2.7                            | Step 2.7              |
| `<OBJECT_KEY>`  | The key of an automatic backup in the bucket; it starts with `vault/` | [Recovering from a lost root key](#recovering-from-a-lost-root-key) | The same section      |

`<HOSTNAME>`, `<ZONE_ID>`, `<ACCOUNT_ID>`, `<DATABASE_ID>`, `<RULESET_ID>` and `<OBJECT_KEY>` are identifiers, not secrets. They may appear in the conversation.

## Part A: Local trial

Part A is optional. It needs Node.js and git, and it creates no Cloudflare resource. The instance and its data stay in this checkout. npm and wrangler write caches under the user's home directory, and wrangler contacts the network to check for updates and, by default, to report usage statistics. Setting the environment variable `WRANGLER_SEND_METRICS=false` turns the statistics off.

### Step A1: Check the tools

Who: Agent

Run:

```
node --version
git --version
```

Verify: Node.js is 22.12 or later. wrangler 4.149.0 requires Node.js 22, and vite 8 requires 22.12. The maintainer uses Node.js 26.5. Any git version works.

Rerun: Safe.

### Step A2: Install dependencies

Who: Agent

Run:

```
npm ci
```

Verify: The command exits with status 0.

Recent npm versions block the install scripts of `esbuild` and `workerd` and print a warning that starts with `npm warn install-scripts`. This is expected, and every later step works without those scripts. Do not approve them.

Rerun: Safe. It replaces `node_modules`.

### Step A3: Build the console

Who: Agent

Run:

```
npm run build:web
```

Verify: The command exits with status 0, and an existence check on `apps/web/dist/index.html` prints `True`.

Rerun: Safe.

### Step A4: Prepare the local instance

Who: Agent

On Windows, first check the length of the checkout path:

```
node -e "console.log(process.cwd().length)"
```

The path of the local database file is 136 characters longer than the path of the checkout, and Windows limits a path to 260 characters, so the number printed must be at most 120. If it is larger, stop and tell the human that the checkout has to move to a shorter path, such as a directory directly below the drive root.

Run:

```
npm run deploy -- --local
```

The command works only on the local configuration at the top level of `wrangler.jsonc`. It creates `.dev.vars` with a new root key unless the file exists, applies the migrations to the local database, and writes a bootstrap token to `work/local-bootstrap.token`. An existing `.dev.vars` with a valid key is kept, because the local database can only be decrypted with it.

Verify: The command exits with status 0 and prints no secret value. Its output contains `Created .dev.vars with a new root key; do not paste it into agent chat or logs.`, or, in a checkout that was set up before, `.dev.vars already exists with a valid ROOT_KEY; it is left as it is.` Its last line is `Bootstrap token written to work/local-bootstrap.token; open /setup and enter it there.` Existence checks on `.dev.vars` and `work/local-bootstrap.token` both print `True`.

Rerun: Safe. It keeps `.dev.vars`, skips the migrations that are applied, and replaces the token file with a new token. On a local instance that already has an Owner, the new token resets the Owner's password instead of creating an Owner, and it expires after one hour.

If it fails:

- `deploy: .dev.vars has no valid ROOT_KEY: it is from an older version of this project and must be replaced.` followed by more text: the file was created by a commit before 0.5.0. Stop and ask the human. Deleting `.dev.vars` is the human's decision, and the local instance then starts empty. After the human has deleted it, run this step again.
- On Windows, the command fails and wrangler's output shows only `internal error; reference = …`: the checkout path is too long, as described at the start of this step. Stop and tell the human that the checkout has to move to a shorter path. The failed run has already created `.dev.vars`; a later run in the same checkout keeps it.

### Step A5: Start the service

Who: Agent

First run `curl -sS --noproxy localhost http://localhost:8787/healthz`. If it already answers as described under Verify, the service is running: skip to Step A6.

Run: Start this command as a background process and leave it running. Record the process ID of the `npm run dev` process itself; stopping the service later needs it. The process that listens on port 8787 is `workerd`, a descendant of that `npm` process. If you only know the port's owner, follow its parent processes up to the `npm` process that runs `npm run dev` and record that one.

```
npm run dev
```

Verify: Within 60 seconds, this request answers as shown.

```
curl -sS --noproxy localhost http://localhost:8787/healthz
```

In a new checkout it prints `{"ok":true,"service":"clavifer","version":"0.5.0","keys":"uninitialized","initialized":false}`. `version` is the version of the code that is running; this release is 0.5.0. In a checkout that already has an Owner it prints `"keys":"ok"` and `"initialized":true`, and Step A6 is then skipped.

The local configuration fixes the origin to `http://localhost:8787`. The console works only at exactly this address: not at the numeric loopback address, and not on another port. The `Ready on` line in wrangler's startup log shows the numeric loopback address; do not copy the address from the log when you tell the human where to go.

The startup log also announces the local data interface named under [Secrets never pass through the agent](#secrets-never-pass-through-the-agent). Do not call it.

Rerun: Do not start a second copy while the first one runs.

### Step A6: Create the Owner

Who: Human

First run `curl -sS --noproxy localhost http://localhost:8787/healthz`. If it prints `"initialized":true`, the Owner already exists: skip this step. The token works only once, so do not send the human to the form again.

If the human asks you to fill in the form in their place, never run code that prints the token or shows it in the conversation; it goes from the file into the page's input field without being echoed.

Say to the human:

> The local instance is running. Please do the following yourself.
>
> 1. Open `work/local-bootstrap.token` in your own editor and copy its content. Do not paste it into this conversation.
> 2. Open `http://localhost:8787/setup` in your browser. The page shows the heading 设置管理员 (set up the administrator). Paste the token into 一次性令牌 (one-time token) and press 继续 (continue).
> 3. The page shows 创建管理员 (create the administrator). Fill in 姓名 (name), 邮箱 (email) and 新密码 (new password, at least 12 characters). The email is your sign-in name; nothing is sent to it, and there is no password recovery by email. Save the password in your password manager.
> 4. 备份公钥 (backup public key) takes the age public key that backups are encrypted to. If you have one whose private key is stored safely, paste it; it starts with `age1`. Otherwise press 在浏览器里生成密钥对 (generate a key pair in the browser), then 下载私钥 (download the private key). Save the content of the downloaded file in your password manager, delete the file, and tick 私钥已保存到 Cloudflare 之外的地方 (the private key is saved outside Cloudflare). Without this private key no backup can be read.
> 5. Press 创建管理员 (create the administrator). The page signs you in and shows the console.
> 6. Delete `work/local-bootstrap.token`. The token cannot be used again.
>
> Tell me when the console is showing and the file is deleted.

Verify:

```
curl -sS --noproxy localhost http://localhost:8787/healthz
```

It prints `"keys":"ok"` and `"initialized":true`. An existence check on `work/local-bootstrap.token` prints `False`.

Rerun: Not possible. Creating the Owner spends the token, and the page then reports that the token is wrong, expired or already used.

### After the trial

If the human also wants a deployment, ask now whether to continue. If the human agrees, start at [Part B](#part-b-production-deployment).

To connect an agent host to the local instance, follow [clients.md](clients.md) with `http://localhost:8787` as `<SERVER>`. Do not use the default names for it: they would be taken when a deployment is connected later. Use a profile name such as `local-claude` and an MCP server name such as `clavifer-local`, as described under [Connecting a second environment](clients.md#connecting-a-second-environment).

To stop the service, end the `npm` process recorded in Step A5 together with its whole tree of child processes. Use the process ID only, never a process name.

Windows:

```
taskkill /PID <PID> /T /F
```

POSIX (unverified):

```sh
kill <PID>
```

On POSIX, npm passes the signal on to wrangler, which stops its own child processes. Then confirm that the port no longer answers:

```
curl -sS --noproxy localhost http://localhost:8787/healthz
```

The command must fail with a connection error. If it still prints a response, stop and ask the human. If this session did not start the service and has no process ID, ask the human to stop it.

The local database stays in `.wrangler/` and is used again the next time the service starts. Discarding the local instance means deleting `.wrangler/` and `.dev.vars`; that is the human's decision.

## Part B: Production deployment

### Phase 1: Prerequisites

Authentication comes first among the steps that need the human, because one of its two options makes the human restart the agent host, and at that point there is nothing yet to carry over. Steps 1.3 to 1.5 are Human steps; the agent may send their messages together and wait for all the answers.

#### Step 1.1: Check the tools and install dependencies

Who: Agent

If the local instance of Part A is running from this checkout, stop it first: `npm ci` replaces `node_modules` while the service is using it. To find out, run `curl -sS --noproxy localhost http://localhost:8787/healthz`. If it answers, stop the service as described under [After the trial](#after-the-trial).

Then perform Steps A1 and A2 of Part A. If this session has just performed them in Part A, they need not be repeated.

Phase 4 builds the command line client on this machine. Check its tools now, so that a missing tool does not surface after the cloud resources exist. Skip this only if the human has said that no agent host will be connected from this machine.

```
go version
pwsh --version
claude --version
codex --version
```

`go version` must succeed, as described in Step 1 of [clients.md](clients.md). `pwsh --version` is needed on Windows only and must print PowerShell 7 or later. Of the last two, run the one for the agent host that will be connected: `claude` for Claude Code, `codex` for Codex. If a command that is needed fails, stop and ask the human to install the tool.

#### Step 1.2: Authentication for wrangler

Who: Agent checks; Human decides and authenticates

wrangler is Cloudflare's command line tool. It may already hold a login on this machine, and that login can belong to another account than the one the human means, such as an employer's. So look first, and never continue with an existing login without asking.

Run:

```
npx wrangler whoami --json
```

If the command exits with status 0 and prints `"loggedIn": true`, say to the human, filling in `authType`, `email` if present, and the `name` and `id` of every entry in `accounts`:

> wrangler is already logged in on this machine: `<authType>`, `<email>`. It can act on these Cloudflare accounts: `<name>` (`<id>`), … Do you want me to deploy with this login, and into which of these accounts? Or do you want to set up a different login?

When the check for `CLOUDFLARE_API_TOKEN` from [Secrets never pass through the agent](#secrets-never-pass-through-the-agent) prints `False`, the login is a browser login. Then add to the message:

> If we keep this browser login and Step 2.7 finds that your domain injects Web Analytics into the pages, you will have to create one rule by hand in the Cloudflare dashboard to turn that off. With an API token I could create it myself.

If the human keeps this login, the step is done. Note whether the human named an account; Step 2.1 uses that.

If the human wants a different one, or if the command exited with a non-zero status because wrangler is not logged in, send the message below. Its Option B has two forms, because wrangler refuses a browser login while `CLOUDFLARE_API_TOKEN` is set and prefers the token over an existing browser login. Send the first form when the check for the variable prints `False`, the second when it prints `True`.

> I need wrangler, Cloudflare's command line tool, to act on your account. Please choose one of two ways. In both, do not paste any token into this conversation.
>
> Option A is an API token. With it I can also create the rule myself that Step 2.7 may need.
>
> 1. In the Cloudflare dashboard, open My Profile > API Tokens > Create Token and start from the template "Edit Cloudflare Workers".
> 2. Add two permissions: Account · D1 · Edit, and Zone · Config Rules · Edit.
> 3. Under Zone Resources select the one domain that will serve Clavifer. Under Account Resources select the one account.
> 4. Open a terminal, set the variable below, and start your agent host from that same terminal, so that my commands inherit it. A session that is already running does not see the variable.
> 5. In the new session, say: "Continue docs/deploy.md at Step 1.2. I have set CLOUDFLARE_API_TOKEN in this terminal."
>
> PowerShell 7:
>
> ```powershell
> $env:CLOUDFLARE_API_TOKEN = Read-Host -MaskInput 'Cloudflare API token'
> ```
>
> bash or zsh:
>
> ```sh
> read -rs CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN
> ```
>
> Option B is a browser login. If Step 2.7 finds that a rule is needed, you will have to create it by hand.
>
> First form: In your own terminal, in this repository, run `npx wrangler login` and approve the request in the browser. You do not need to restart anything.
>
> Second form: An API token is set in the terminal that started this session, and wrangler uses it in preference to a browser login. Start your agent host again from a terminal in which `CLOUDFLARE_API_TOKEN` is not set. In this repository, run `npx wrangler login` and approve the request in the browser. In the new session, say: "Continue docs/deploy.md at Step 1.2. I have logged in to wrangler with the browser."
>
> Tell me which option you used.

The permission names above are the ones Cloudflare's documentation gives for the dashboard. Whether the token page currently shows these names or Cloudflare's newer Workers role names is unverified.

Verify: This check is for a login that the human set up during this session, which is the first form of Option B. A login the human chose to keep is already confirmed, and a session that continues after a restart confirms it with the question at the top of this step. Run `npx wrangler whoami --json` again. It must exit with status 0 and print `"loggedIn": true`, but that alone does not complete the step. Show the human `authType`, `email` if present, and the `name` and `id` of every entry in `accounts`, and ask whether this is the login they meant. The step is done when the human confirms. Step 2.1 then settles the account.

Rerun: Safe. A session that continues here after a restart starts this step from the top. Its first command shows the new login, and the question that follows it is this confirmation.

#### Step 1.3: Cloudflare account and plan

Who: Human

Say to the human:

> You need a Cloudflare account on the Workers Paid plan, which has a monthly fee. Clavifer seals old records, writes backups, and imports and exports its data in single requests and scheduled runs that need up to 30 seconds of CPU time and up to 1000 database queries; the Workers Free plan allows 10 ms and 50. Is the account on Workers Paid, or will you move it there?
>
> The database and the backup bucket are created in Cloudflare's default location. If the data must stay in a particular region or jurisdiction, tell me now.

Verify: The agent cannot check the plan. Continue when the human confirms Workers Paid. If the human wants to stay on Workers Free, stop: the deployment cannot work there. If the human names a region or jurisdiction, Steps 2.3 and 2.4 use it.

#### Step 1.4: Zone and hostname

Who: Human

Say to the human:

> Clavifer is served on a hostname of your own. You need a domain that is in the same Cloudflare account, uses Cloudflare for DNS, and shows as Active in the dashboard. Choose a hostname under it that is not in use, such as `vault.` followed by your domain. Do not create a DNS record for it; the deployment creates the record and the certificate.
>
> Please tell me the hostname, and the Zone ID of the domain. The Zone ID is on the domain's Overview page in the Cloudflare dashboard.

Verify: The human has given `<HOSTNAME>` and `<ZONE_ID>`. The deploy entry in Step 2.6 checks that the hostname is free.

#### Step 1.5: Enable R2

Who: Human

Say to the human:

> Encrypted backups are stored in Cloudflare R2. R2 must be enabled once per account, in the dashboard, by you: open Storage & databases > R2 > Overview and complete the checkout. R2 has a free allowance and bills for use beyond it. Tell me when R2 is enabled.

Verify: Step 2.4 checks this.

### Phase 2: Provision and deploy

The steps in this phase are Agent steps, with two exceptions. Step 2.1 needs the human's confirmation. In Step 2.7, creating the rule goes to the human when no API token is set in your shell, or when the token lacks the permission.

#### Step 2.1: Confirm the account

Who: Agent, with the human's confirmation

Run:

```
npx wrangler whoami --json
```

Verify: The command exits with status 0 and prints a JSON object with `"loggedIn": true` and an `accounts` array of `id` and `name`.

If the human already named the account in Step 1.2, by name or by ID, check that `accounts` still contains it. If it does, its `id` is `<ACCOUNT_ID>`, and there is no need to ask again. If it does not, stop and ask the human.

If the human has not named an account, then, whatever the number of entries, say to the human, with the `name` and `id` of every entry in `accounts`:

> wrangler can act on these Cloudflare accounts: `<name>` (`<id>`), … Which one should Clavifer be deployed into? Please confirm even if there is only one.

Wait for the answer. The `id` of the account the human names is `<ACCOUNT_ID>`. If `accounts` has no entry, stop and ask the human.

The top-level keys of the object are `loggedIn`, `authType`, `email`, `accounts` and `tokenPermissions`. For a browser login, `authType` is `"OAuth Token"`.

Rerun: Safe.

If it fails:

- Non-zero exit status, or a message that `CLOUDFLARE_API_TOKEN` is necessary in a non-interactive environment: wrangler is not authenticated in your shell. Return to Step 1.2.

#### Step 2.2: Write the account into the configuration

Who: Agent

Every later command must act on the same account. wrangler takes the account from `account_id` in `wrangler.jsonc` first, then from the environment variable `CLOUDFLARE_ACCOUNT_ID`, then from its cached login. The template's `account_id` is all zeros, a placeholder that makes every wrangler command that acts on an account fail, and the deploy entry refuses to run while it is there. Writing the account into the configuration before anything is created makes the configuration decide the account for every command this document uses, whatever `CLOUDFLARE_ACCOUNT_ID` is set to.

The deployment keeps its own values in `wrangler.jsonc`, as commits on a local branch named `deploy`.

Run: Create the branch.

```
git switch -c deploy
```

If git answers that the branch `deploy` already exists, run `git switch deploy` instead.

Then change one line at the top level of `wrangler.jsonc`, directly below the line `"name": "clavifer",`:

```jsonc
  "account_id": "00000000000000000000000000000000",
```

becomes

```jsonc
  "account_id": "<ACCOUNT_ID>",
```

A value at the top level is inherited by every environment, and also applies to commands that take no `--env`, such as `d1 create` and `r2 bucket create`. The account ID is an identifier, not a secret.

Verify:

```
git diff -- wrangler.jsonc
```

The diff shows exactly one changed line, the `account_id` line above the `env` block. Then commit:

```
git commit -m "Deployment account" -- wrangler.jsonc
```

Do not push this branch yourself. It holds identifiers, not secrets, so the human may push it to a private remote of their own to keep it safe. It must not go to a public fork.

Rerun: If `git diff main -- wrangler.jsonc` already shows this line with `<ACCOUNT_ID>`, the step is done. If it shows the line with a different ID, stop and ask the human.

If it fails:

#### Step 2.6: Deploy

Who: Agent

Run:

```
npm run deploy -- --env production
```

The deploy entry does the following, in this order, and stops at the first refusal:

1. It reads the `production` environment of `wrangler.jsonc` and refuses placeholders and inconsistent values.
2. It reads, without changing anything, the Worker that has this name, its bindings and secrets, which Worker the hostname is attached to, whether the hostname resolves in DNS, and whether the database already holds an instance. It refuses when deploying would rebind the Worker, take the hostname from another Worker, overwrite a DNS record, or put a new key on data that already exists.
3. For a database that holds no instance yet and a Worker without `ROOT_KEY`, it generates the key and stores it on the Worker. The key is not written anywhere else and not printed.
4. It applies the database migrations and checks that every migration in `migrations/` is recorded in the database.
5. It builds the console and deploys the Worker.
6. While the instance has no Owner, it writes a new bootstrap token to `work/production-bootstrap.token`. The token is valid for 24 hours.
7. It waits up to 10 minutes until `https://<HOSTNAME>/healthz` reports this version.

On a first deployment the command can run for more than 10 minutes while Cloudflare issues the certificate for the hostname. Give it a timeout of at least 15 minutes, or run it in the background and wait until it exits.

Verify: The command exits with status 0 and prints no secret value. Between wrangler's own output, it prints `Stored a new ROOT_KEY on the Worker; it exists nowhere else.` (only on the run that stores the key) and `Bootstrap token written to work/production-bootstrap.token; open /setup and enter it there.` Its last line is `https://<HOSTNAME> runs 0.5.0, uninitialized.` An existence check on `work/production-bootstrap.token` prints `True`.

Rerun: Safe. Each run reads the live state again. A run after a failure continues where the earlier one stopped: it does not generate a second key for a Worker that has one, and while the instance has no Owner it issues a new token, which replaces the earlier one and its file. Once the Owner exists, a run deploys the checked-out code without a token, as in [Upgrading](#upgrading).

If it fails: The configuration checks come first and change nothing.

- `account_id in wrangler.jsonc is missing or the template's all-zero placeholder; …`: Step 2.2 is not done.
- `env "production" still has the template's all-zero database_id; …`, `env "production" still has the template's hostname credentials.example.com; …` or `APP_ORIGIN of env "production" is …`: Step 2.5 is incomplete.
- `env "production" has no database_id for the D1 binding DB`, `… has no R2 bucket for the binding BACKUPS`, `… must have exactly one route, and it must be a custom domain`, `… has no cron trigger; …`, `… does not declare "secrets": { "required": ["ROOT_KEY"] } …` or `… sets ALLOW_LOCAL_HTTP to "true", …`: the `env.production` block differs from the template in more than the values of Step 2.5. Show the human `git diff main -- wrangler.jsonc` and stop.
- `env "…" and env "…" share the <field> <value>`: two environments name the same Worker, database, bucket or hostname. Each environment needs its own. Stop and ask the human.

The checks of the live state change nothing either.

- A message that names code 7403 or 10013: the deploy entry has already retried once. Run the command again. If it fails three times in a row, stop.
- `wrangler auth token failed: …`, or another `wrangler … failed:` line that reports missing authentication: wrangler is not authenticated in your shell. Return to Step 2.1.
- `wrangler is signed in with CLOUDFLARE_API_KEY and CLOUDFLARE_EMAIL; use an API token or wrangler login`: return to Step 1.2 and use one of its two options.
- `GET /workers/domains?hostname=… failed: …` with an authentication or permission error: the API token lacks a permission that the deploy entry needs to read the Workers custom domains. Which permission this is has not been verified. Stop, show the human the error, and offer Option B of Step 1.2 as the alternative.
- `the DNS lookup of <HOSTNAME> (…) failed`: run the command again. If it fails a second time, stop.
- `<HOSTNAME> already resolves in DNS but is not a custom domain of any Worker; deploying would overwrite its DNS record`: the hostname has an address record or an alias, or a wildcard record of the domain covers it. Without a terminal, `wrangler deploy` would replace that record without asking. Stop and ask the human which of two ways to go. Another hostname: the human names it, you change the two hostname values of Step 2.5, commit, and run this step again. This hostname: the human deletes the record in the Cloudflare dashboard, and you run this step again.
- `<HOSTNAME> is attached to the Worker …; deploying would move it to clavifer-production`: another Worker serves this hostname. Stop and ask the human to choose another hostname or to detach it from that Worker.
- `the Worker clavifer-production exists but has neither the D1 and R2 bindings of this configuration nor a ROOT_KEY, so it is not a Clavifer instance of this configuration and deploying would replace it; …`: a Worker with this name exists that this procedure did not set up, and deploying would replace its code. A run of this step that failed at `wrangler secret put ROOT_KEY` can also leave such a Worker behind, with no code of its own. Stop and ask the human whether that Worker is needed. If it is not, the human deletes it in the Cloudflare dashboard. If it is, the human renames it there, or chooses another Worker name, which goes into `name` in the `env.production` block and is committed as in Step 2.5. Then run this step again.
- `the Worker clavifer-production has the D1 binding …, not DB=…; deploying would rebind it`, or the same with `the R2 binding`: a Worker with this name uses another database or bucket than the configuration names. Either the configuration is wrong or the Worker is not this deployment's. Stop and ask the human.
- `the database … is initialized, but the Worker clavifer-production does not exist; deploying would give its data a new root key`, or the same with `is only a placeholder`: `database_id` names a database that already holds an instance. Compare it with the `uuid` of Step 2.3, then stop and ask the human.
- `the Worker clavifer-production has no ROOT_KEY, but its database is initialized and needs the key it was set up with; …`: the Worker has lost its key, or it was deployed from a commit before 0.5.0 (see [Upgrading](#upgrading)). Stop and ask the human.

The remaining failures come after the key may have been stored. Running the command again is safe for each of them.

- `the database lists the migrations …, but migrations has …; stopping before deploying`: the migrations did not all apply. Run the command again once. If the message repeats, stop.
- `npm run build:web failed`: the build output above the message names the error. Stop and show it to the human.
- `wrangler secret put ROOT_KEY failed: …` or `wrangler deploy failed: …` with an error about authentication or permissions while wrangler uses an API token: it is unverified whether a token built from the "Edit Cloudflare Workers" template can create a Worker that does not exist yet, and whether attaching the hostname needs further zone permissions. Stop, show the human the error, and offer Option B of Step 1.2 as the alternative.
- `https://<HOSTNAME>/healthz did not answer … within 10 minutes; last: …`: if `last` names a TLS or connection error, the certificate is not ready yet; wait five minutes and run the command again. Stop if it fails the same way a third time, or if `last` shows an answer with other values.

#### Step 2.7: Turn off Web Analytics injection for the hostname

Who: Agent detects and verifies. The rule is created by the Agent when an API token is set in the agent's shell, otherwise by the Human.

On zones of the Free plan, Cloudflare injects its Web Analytics script into HTML pages by default. The console's pages allow only their own scripts, so the browser blocks the injected script and reports a content security policy violation on every page load. A configuration rule turns the injection off for this hostname.

Run: First detect whether the zone injects.

```
curl -sS -H "Accept: text/html" https://<HOSTNAME>/
```

The output is a short HTML document. Decide by whether it contains the string `cloudflareinsights`:

- It does not: the zone is not injecting into this hostname. The step is done; create no rule.
- It does: create the rule as described below.

This check rests on what the maintainer observed in one deployment, not on a guarantee by Cloudflare. There, on a zone of the Free plan, a new hostname was injected by default, the string appeared only when the request carried `Accept: text/html`, and it was gone within ten seconds after the rule was added.

To find out who creates the rule, run the check for `CLOUDFLARE_API_TOKEN` from [Secrets never pass through the agent](#secrets-never-pass-through-the-agent). If it prints `False`, or if any request below fails with an authentication or permission error, say to the human:

> Please create one rule in the Cloudflare dashboard. Open the domain, go to Rules, and create a Configuration Rule. Match requests where Hostname equals `<HOSTNAME>`. In the settings, turn on the one Cloudflare's documentation calls "Disable Real User Monitoring (RUM)". Deploy the rule and tell me when it is active. Reference: https://developers.cloudflare.com/rules/configuration-rules/settings/

After the human confirms, continue at Verify.

If the check prints `True`, the agent creates the rule. The maintainer has run the list request and Case 2 below, on a zone that already had configuration rules, with a different kind of credential than the API token. Case 1, and whether a token with Zone · Config Rules · Edit is sufficient, are unverified.

List the rulesets of the zone. The commands name the token's variable and the shell fills in its value, which the rules for secrets allow.

PowerShell:

```powershell
curl -sS -H "Authorization: Bearer $env:CLOUDFLARE_API_TOKEN" "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets"
```

POSIX:

```sh
curl -sS -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets"
```

The response has `"success": true` and a `result` array. Look for the entry with `"phase": "http_config_settings"` and `"kind": "zone"`. Then follow the case that applies. In the commands below, `<AUTH>` stands for the same `-H "Authorization: Bearer …"` argument as above, in the form for your shell.

Case 1, no such entry (unverified): the zone has no configuration rules. Write this to a new file `rum-rule.local.json` in the repository root, which git ignores:

```json
{
  "rules": [
    {
      "description": "Clavifer: no Web Analytics injection",
      "expression": "http.host eq \"<HOSTNAME>\"",
      "action": "set_config",
      "action_parameters": { "disable_rum": true }
    }
  ]
}
```

Then run:

```
curl -sS -X PUT <AUTH> -H "Content-Type: application/json" --data "@rum-rule.local.json" "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets/phases/http_config_settings/entrypoint"
```

Case 2, the entry exists: its `id` is `<RULESET_ID>`. Do not use the `PUT` request of Case 1: it replaces every configuration rule the zone already has. Read the existing rules first:

```
curl -sS <AUTH> "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets/<RULESET_ID>"
```

The rule counts as present only if `result.rules` holds a rule whose `expression` is exactly `http.host eq "<HOSTNAME>"` whose `action_parameters` has `"disable_rum": true`, and whose `enabled` is `true`. In that case the step is done. In every other case, including a rule that names `<HOSTNAME>` inside a longer expression, write this to `rum-rule.local.json`:

```json
{
  "description": "Clavifer: no Web Analytics injection",
  "expression": "http.host eq \"<HOSTNAME>\"",
  "action": "set_config",
  "action_parameters": { "disable_rum": true }
}
```

Then append it:

```
curl -sS -X POST <AUTH> -H "Content-Type: application/json" --data "@rum-rule.local.json" "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets/<RULESET_ID>/rules"
```

Keep the quotes around `@rum-rule.local.json`: PowerShell reads an unquoted `@` as its own syntax.

The response to the `PUT` or `POST` request has `"success": true`, and its `result.rules` contains the rule for `<HOSTNAME>` next to every rule that was there before. Then delete `rum-rule.local.json`.

Verify: Whoever created the rule, run the detection command from the start of this step again. Within one minute, its output no longer contains `cloudflareinsights`. Repeat it every 10 seconds until then; if the string is still there after one minute, stop.

Rerun: Start from the detection command. Without the string in its output, there is nothing to do.

If it fails:

- `"success": false` with an authentication or permission error: the token probably lacks Zone · Config Rules · Edit. Use the message for the human above.
- `"success": false` because the zone has reached its number of configuration rules (10 on the Free plan): stop and ask the human.

## Staging environment

`wrangler.jsonc` defines a second environment, `staging`, for trying a new version before production. It is a complete, separate deployment: its own Worker, database, bucket, hostname, key and Owner. It is optional.

To create it, perform Part B again with the `staging` column of the table under [Names and placeholders](#names-and-placeholders):

- Skip Step 2.2 if production is already deployed. The `account_id` line at the top level applies to every environment, so both environments are in the same account.
- Use `--env staging` wherever a command has `--env production`.
- Use the database name `clavifer-staging` and the bucket name `clavifer-staging-backups`.
- Use `staging` in place of `production` in every file name under `work/`.
- In Step 2.5, edit the `env.staging` block. Its template hostname is `credentials-staging.example.com`. The check of that step then reads: the diff shows three changed lines, all between `"staging": {` and `"production": {`, and the `production` block and the top level are unchanged.
- In Step 2.7, use the staging hostname. If a rule is needed, the step adds one for it and keeps the rules that exist.
- In [clients.md](clients.md), use a different profile name and a different MCP server name, as described under [Connecting a second environment](clients.md#connecting-a-second-environment).

## Upgrading

An upgrade deploys new code over a running environment. Its key and data stay as they are. If a staging environment exists, upgrade it first, with `staging` in place of `production`.

The version to upgrade to is the latest commit of `origin/main`. The project has no separate release branch, and every version has an entry in [CHANGELOG.md](../CHANGELOG.md).

0.5.0 is the first release. An instance whose `/healthz` answer has no `keys` field was deployed from a pre-release commit of the repository, even if it reports `version` 0.5.0, and cannot be upgraded in place: 0.5.0 replaces its Worker secrets with `ROOT_KEY` and starts the database schema anew. Do not deploy 0.5.0 over it. If its 备份 (backup) page offers 完整导出 (full export), import that export into a new 0.5.0 instance, as described under [Migrating to a new instance](#migrating-to-a-new-instance). Otherwise deploy a new instance with Part B, and the human enters the data again.

Steps U1 to U3 are Agent steps. In Step U4 the human installs the client. With a staging environment, perform Steps U1 and U2 once, Step U3 for staging, then Step U3 for production, and Step U4 once, after every environment is upgraded.

### Step U1: Get the new code

Run:

```
git switch deploy
git fetch origin
git merge origin/main
```

Then read the entries of [CHANGELOG.md](../CHANGELOG.md) between the old and the new version. The old version is the `version` that `curl -sS https://<HOSTNAME>/healthz` reports before the upgrade; the new one is the topmost entry of `CHANGELOG.md`. If the answer has no `version`, no `keys`, or a version before 0.5.0, stop and see the paragraph above these steps. Follow any upgrade note there before continuing.

Verify: The merge completes, and `git diff origin/main -- wrangler.jsonc` shows only the `account_id` line from Step 2.2 and the values written in Step 2.5, or later by a migration within the same account or a recovery: the names in `name`, `d1_databases[0].database_name` and `r2_buckets[0].bucket_name`, and the `database_id`.

If it fails:

- `git switch deploy` fails because the branch does not exist: see [If the deploy branch is gone](#if-the-deploy-branch-is-gone).
- `git fetch origin` fails, or `origin` is not the Clavifer repository: stop and ask the human where the new version comes from.
- A merge conflict in `wrangler.jsonc`: stop and ask the human.

### Step U2: Install dependencies

Run:

```
npm ci
```

Verify: The command exits with status 0.

### Step U3: Deploy

Run:

```
npm run deploy -- --env production
```

The deploy entry performs the same checks as in Step 2.6. On an environment whose Owner exists, it leaves `ROOT_KEY` as it is, applies the migrations before it deploys the code, and issues no token. Migrations go first because new code that runs against an old schema fails on missing columns.

Verify: The command exits with status 0. Its last line is `https://<HOSTNAME> runs <version>.`, where `<version>` is the version this upgrade goes to, the topmost entry of `CHANGELOG.md`.

Rerun: Safe. Until a deployment succeeds, the previous version stays live.

If it fails: follow the entries of Step 2.6.

### Step U4: Update the command line client

Who: Agent builds and verifies; Human installs

Follow [Updating the client](clients.md#updating-the-client) in clients.md on every machine that uses this environment. The agent builds the client and updates the Skill; the human closes the agent hosts and runs the install script, because the agent's own agent host keeps the installed executable in use; a new session verifies. This step ends the current session, so it comes last.

### If the deploy branch is gone

The branch `deploy` exists only where it was created, unless the human pushed it to a private remote. In a new checkout, first ask the human whether such a remote has it. If it does, the human fetches it, and `git switch deploy` works.

Otherwise rebuild the branch. Nothing here creates or changes anything in Cloudflare.

1. Perform Steps 1.1 and 1.2, then Steps 2.1 and 2.2. They confirm the account, create the branch and write `account_id`.
2. Run `npx wrangler d1 list --json`. The deployment's database is `clavifer` unless a migration within the same account or a recovery gave it another name, such as `clavifer-2`; the same holds for the Worker and the bucket. If the list has no `clavifer`, or also has such a second name, ask the human which database the deployment uses. Its `uuid` is `<DATABASE_ID>`. Do not create a database.
3. Ask the human for `<HOSTNAME>`, the hostname that serves the deployment now.
4. Perform the edit, the check and the commit of Step 2.5. If the database, the Worker or the bucket has another name than in the template, also write it into `d1_databases[0].database_name`, `name` or `r2_buckets[0].bucket_name`.
5. If a staging environment exists, repeat points 2 to 4 for it: the database is `clavifer-staging`, the hostname is the staging one, and the edit goes into the `env.staging` block.

Verify: `npx wrangler secret list --env production` prints a list that contains `ROOT_KEY`, which shows that the configuration points at the deployed Worker, and `curl -sS https://<HOSTNAME>/healthz` prints `"ok":true`.

Do not perform any other step of Phase 2. If the database or the bucket in the rebuilt configuration differs from the ones the Worker uses, the deploy entry refuses to deploy.

Then continue with Step U1.

## Changing the hostname

A hostname can be attached to only one Worker at a time. To move the service to a new hostname:

1. In `wrangler.jsonc`, change `routes[0].pattern` and `vars.APP_ORIGIN` of the environment, as in Step 2.5, and commit.
2. Run `npm run deploy -- --env production`. It checks that the new hostname is free, as in Step 2.6, and waits until the service answers on it. Then perform Step 2.7 for the new hostname.
3. The human signs in at the new hostname with the password and registers every Passkey again. A Passkey is bound to the hostname it was registered on.
4. Log in again with every profile, as in the login step of [clients.md](clients.md), with the new address as `<SERVER>`. The client ID stays the same.

When a hostname moves from one environment to another, deploy the environment that gives it up first, confirm that the hostname no longer answers, and then deploy the environment that takes it.

## Removing a deployment

Remove a deployment only when the human asks for it in so many words. Removal deletes every credential stored in it, and nothing brings them back.

Without a terminal, none of the three delete commands waits for anyone: `wrangler delete` and `wrangler d1 delete` answer their own confirmation with yes, and `wrangler r2 bucket delete` asks nothing. So every check comes before the commands. `wrangler delete --dry-run` is no check; it does not show what would be deleted.

The names below are those of production in the template. For staging, use the `staging` column of the table under [Names and placeholders](#names-and-placeholders). After a migration within the same account or a recovery, the names can differ: use the ones in `name`, `d1_databases[0].database_name` and `r2_buckets[0].bucket_name` of the environment's block in `wrangler.jsonc`, in every command and message below.

1. In the checkout that deployed the environment, make sure the configuration points at this deployment:

   ```
   git branch --show-current
   npx wrangler secret list --env production
   npx wrangler d1 list --json
   npx wrangler r2 bucket info clavifer-backups --json
   ```

   The branch is `deploy`. The secret list contains `ROOT_KEY`. The entry whose `name` is the database named in `d1_databases[0].database_name` of `env.production` has the `uuid` that `wrangler.jsonc` holds as `database_id`. The last command exits with status 0. If anything differs, stop.

2. Say to the human:

   > I am about to delete the Worker `clavifer-production`, the database `clavifer` with every stored credential, and the bucket `clavifer-backups` with every automatic backup. This cannot be undone. Do you have a full export and its age private key outside this account, or are you sure you no longer need the data? Please confirm that I should delete.

   Continue only after the human confirms.

3. Delete the Worker, with its name written out. This also removes the hostname, its DNS record, the schedule and `ROOT_KEY`.

   ```
   npx wrangler delete clavifer-production --env production
   ```

   It prints `Successfully deleted clavifer-production`. Afterwards, `npx wrangler secret list --env production` fails with `Worker "clavifer-production" (env: production) not found.`

4. Delete the database.

   ```
   npx wrangler d1 delete clavifer --env production
   ```

   It prints `Deleted 'clavifer' successfully.` Afterwards, `npx wrangler d1 list --json` has no entry named `clavifer`.

5. Delete the bucket.

   ```
   npx wrangler r2 bucket delete clavifer-backups
   ```

   It prints `Deleted bucket clavifer-backups.` Afterwards, `npx wrangler r2 bucket info clavifer-backups --json` fails with `The specified bucket does not exist. [code: 10006]`. The maintainer deleted an empty bucket. A bucket that holds backups or sealed records is expected to refuse deletion, and emptying a bucket is unverified: if the command fails, stop and ask the human.

6. About one minute after the Worker is deleted, the hostname no longer resolves. These two requests then have no `Answer` field:

   ```
   curl -sS -H "accept: application/dns-json" "https://cloudflare-dns.com/dns-query?name=<HOSTNAME>&type=A"
   curl -sS -H "accept: application/dns-json" "https://cloudflare-dns.com/dns-query?name=<HOSTNAME>&type=AAAA"
   ```

   During that minute and for some minutes after it, `curl` to the hostname can still receive a response with a 5xx status and exit with status 0. That response comes from Cloudflare's edge and does not mean the service is running.

7. If Step 2.7 created a rule, remove that one rule and no other. With an API token, read the ruleset as in Case 2 of Step 2.7, take the `id` of the rule whose `expression` is exactly `http.host eq "<HOSTNAME>"`, and send `DELETE` to `https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/rulesets/<RULESET_ID>/rules/` followed by that `id`. The response has `"success": true`, and its `result.rules` holds the remaining rules without the deleted one. Without a token, ask the human to delete the rule in the dashboard.

The files under `work/`, the branch `deploy`, and the logins on client machines are left as they are; the human decides what to do with them. [Disconnecting](clients.md#disconnecting) in clients.md describes how to clear a login whose installation no longer exists.

## Backups, migration and recovery

What the service does, as implemented:

- Every 15 minutes the Worker's scheduled run first seals old records, then checks whether a backup is due. It writes a new automatic backup to the bucket under `vault/` when anything the backup carries has changed since the last successful backup, when the recipient has changed, or when the last successful backup is 24 hours old.
- An automatic backup is a snapshot in the format `clavifer-backup-v1`. It holds the Owner with the password hash and the Passkeys, every secret (an active one with its versions up to the current one; a deleted secret carries no versions), the connections, installations and grants, the access requests and audit rows that are still in the database, the backup recipient, and the key that sealed records are encrypted with. Sealed records are not in it: it names each sealed file by its key in the same bucket. Sessions and tokens are not carried.
- A snapshot is encrypted to the age recipient before it leaves the Worker. It does not depend on `ROOT_KEY`: an import encrypts every secret again under the key of the instance it goes into.
- After each successful backup the Worker deletes older copies under `vault/`. It keeps the newest copy of each of the last 30 days and the newest copy of each of the 12 months before that.
- Audit rows older than five minutes and access requests older than 25 hours are sealed: once the sealable rows of one kind exceed about 1.5 MB, they move out of the database into files of about 1 MB under `archive/` in the same bucket, encrypted to the instance's archive key, an age key generated together with the Owner or carried over by an import. Nothing under `archive/` is ever overwritten or deleted. The archive key is a post-quantum key, but every snapshot carries it, so the sealed records are protected no better than the snapshots: by the backup recipient, or the recipient of a full export. The key pair the console generates is X25519, not post-quantum; for post-quantum protection use a recipient that starts with `age1pq1`.
- When the data a backup carries takes more than 9 MB in the database, the automatic backup is skipped, and the backup page shows 热数据超限，自动备份已跳过 (hot data over the limit, automatic backup skipped). Backups resume once sealing has moved enough rows out. The Owner's account, secrets, connections, installations and grants are never sealed; when they alone pass 6 MB the page shows 接近热数据上限 (close to the hot data limit), and above 9 MB only full exports work.

The bucket is in the same Cloudflare account as the service, and nothing copies data out of the account automatically. A copy that is to survive the loss of the account must be a full export. On 备份 (backup), 完整导出 (full export) writes one file with everything, the sealed records included, encrypted to a recipient entered on the spot, by default the backup recipient. It needs a sign-in within the last 10 minutes, and the export can be relied on only when the panel reports 已全部写出 (written in full). 下载最新的自动备份 (download the latest automatic backup) gives a file that is usable only together with its bucket, because it names the sealed files by their keys. A copy of the bucket made by other means must include `archive/` as well as `vault/`.

### What the human must keep

| Item                                      | If it is lost                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| age private key of the backup recipient   | No backup or full export encrypted to it can be read.                          |
| A recent full export, outside the account | If the Cloudflare account is lost, nothing else brings the data back.          |
| Owner password and Passkeys               | Nobody can sign in until the password is reset. There is no recovery by email. |

`ROOT_KEY` has no copy to keep. If it is lost or overwritten, [Recovering from a lost root key](#recovering-from-a-lost-root-key) rebuilds the instance from the latest automatic backup. When every way to sign in is lost, [Resetting the Owner's password](#resetting-the-owners-password) gives the Owner a new one.

### Migrating to a new instance

A migration moves everything an instance holds into a new instance that has no Owner yet, for example to another account or to another hostname. The human performs the export and the import, because they need the age private key.

1. Who: Human. Say to the human:

   > In the console of the old instance, open 备份 (backup) and press 完整导出 (full export). Enter an age public key whose private key you hold, by default the backup recipient, press 开始导出 (start the export), and wait until the panel shows 已全部写出 (written in full). Changes made in the old instance after the export do not reach the new one. Tell me when the export is written in full.

2. Who: Agent. Create the new environment with Part B through Step 2.7, in a new clone of the repository with its own `deploy` branch. The branch of the old environment keeps the old account and names, and Part B stops on them.

   In the same account, the names Part B uses are taken by the old environment. Choose new names for the Worker, the database and the bucket, for example with the suffix `-2`: `clavifer-production-2`, `clavifer-2`, `clavifer-backups-2`. Use the database and bucket names in Steps 2.3 and 2.4 in place of `clavifer` and `clavifer-backups`. In Step 2.5, also write the three names into `name`, `d1_databases[0].database_name` and `r2_buckets[0].bucket_name` of the `env.production` block. Every later command that names the database or the bucket uses the new names.

   The new environment needs a hostname of its own. To keep the old hostname, the old environment has to give it up first, as described under [Changing the hostname](#changing-the-hostname).

3. Who: Human. In place of Step 3.1, say to the human:

   > 1. Open `work/production-bootstrap.token` in your own editor and copy its content. Do not paste it into this conversation.
   > 2. Open `https://<HOSTNAME>/setup` in your browser, paste the token into 一次性令牌 (one-time token) and press 继续 (continue).
   > 3. Press 从快照导入（迁移或灾备恢复） (import from a snapshot, for a migration or a disaster recovery).
   > 4. Choose the export under 快照文件 (snapshot file), paste the age private key, which starts with `AGE-SECRET-KEY-`, into 备份私钥 (backup private key), and press 开始导入 (start the import). The browser decrypts the file; the private key is not sent to the server.
   > 5. When the import is done, sign in with the email and password of the old instance.
   > 6. Delete `work/production-bootstrap.token`.
   >
   > Tell me when you are signed in and the file is deleted.

   Verify: `curl -sS https://<HOSTNAME>/healthz` prints `"keys":"ok"` and `"initialized":true`. An existence check on `work/production-bootstrap.token` prints `False`.

   If the import fails, the instance stays without an Owner and the token is spent. Perform Step 2.6 again, which issues a new token, and repeat this point.

4. Passkeys are carried over only when the new hostname is the same as the old one. Otherwise perform Step 3.2. Then perform Step 3.3; the backup recipient comes from the export.
5. Every installation keeps its client ID. Log in again with every profile, as in the login step of [clients.md](clients.md), with the new address as `<SERVER>`. Web-based MCP clients authorize again.

The old environment stays as it is until the human decides to remove it, as described under [Removing a deployment](#removing-a-deployment).

### Recovering from a lost root key

When the Worker's `ROOT_KEY` is lost or overwritten, every route but `/healthz` answers `503 root_key_mismatch`, and `/healthz` reports `"keys":"mismatch"`. A key that cannot be parsed makes every route, `/healthz` included, answer `{"error":"invalid_root_key"}`. The data in the database cannot be decrypted without the old key, and there is no copy of it. Recovery puts a new key and a new database on the Worker and imports the latest automatic backup from the same bucket. Everything written after that backup is lost. Perform this only when the human asks for it.

The same procedure recovers a second situation: the D1 database the Worker is bound to was deleted, while the key is intact. Then every route, `/healthz` included, answers `{"error":"internal_error",…}`, and the data went with the database. The old key is not needed, because the import encrypts the backup's values under the new key.

If the Cloudflare account itself is lost, this procedure does not help; only a full export kept outside the account does.

1. Who: Agent. Confirm the loss:

   ```
   curl -sS https://<HOSTNAME>/healthz
   ```

   It prints `"keys":"mismatch"` or `"error":"invalid_root_key"`: the key is lost; continue with point 2. If it prints `"error":"internal_error"`, check whether the database was deleted, with the `database_id` of the `env.production` block of `wrangler.jsonc` as `<DATABASE_ID>`:

   ```
   npx wrangler d1 info <DATABASE_ID> --env production
   ```

   It fails with `Couldn't find a D1 DB with name or binding '<DATABASE_ID>' in your config or the API.`: the database was deleted. Skip point 2, since there is no database to read, and continue with point 3. With any other answer to either command, stop: this procedure does not apply, and the deploy entry refuses `--rebuild`.

2. Who: Agent. Before the configuration changes, read which backup the instance recorded as its latest from the old database, which is readable without the key:

   ```
   npx wrangler d1 execute DB --env production --remote --json --command "SELECT object_key FROM backup_state WHERE id=1"
   ```

   The command names the database by its binding `DB`, not by its name: wrangler looks up a name that is not in the configuration across the whole account. The output is a JSON array; `object_key` in the first row of `results` of its first entry is `<OBJECT_KEY>`. If it is `null`, the instance never completed a backup: stop and ask the human.

3. Who: Agent. Create a new database. Choose a name that `npx wrangler d1 list --json` does not list yet, such as `clavifer-2`, and create it as in Step 2.3. In the `env.production` block of `wrangler.jsonc`, change `d1_databases[0].database_name` to the new name and `d1_databases[0].database_id` to its `uuid`. Leave the bucket as it is. Commit as in Step 2.5.

4. Who: Agent. Run:

   ```
   npm run deploy -- --env production --rebuild
   ```

   The deploy entry checks `/healthz` again and refuses unless it reports the key lost or wrangler reports every database the Worker is bound to as deleted, and it refuses a database that already holds an instance. It then binds the Worker to the new database, stores a new `ROOT_KEY`, applies the migrations, deploys, issues a token, and waits for `/healthz`. Give it the same timeout as in Step 2.6.

   Verify: The command exits with status 0. It prints `Stored a new ROOT_KEY on the Worker; it exists nowhere else.`, the line with the token file, `https://<HOSTNAME> runs 0.5.0, uninitialized.`, and `Latest automatic backup: ` followed by the key of the newest object under `vault/`, with a command to fetch it.

   The newest object is normally `<OBJECT_KEY>`. If it differs, use `<OBJECT_KEY>`: a newer object can be one encrypted to an earlier recipient, written while the recipient was being changed, which the instance never recorded as a backup. After a deleted database, point 2 was skipped: use the newest object as `<OBJECT_KEY>`, and if the page in point 6 cannot decrypt it with the current backup private key, fetch the next older object under `vault/` and try again. Keys under `vault/` sort by the time of the backup. wrangler has no command that lists objects, so ask the human to read the next older key from the bucket's object list in the Cloudflare dashboard.

   If the output ends with `<bucket> has no automatic backup under vault/.` instead, there is nothing to import from the bucket: stop and ask the human. A full export kept outside the account is then the only source of the data.

   If it fails: `… not a lost or replaced root key, and …; --rebuild is only for an instance whose root key is lost or replaced or whose database was deleted`: stop. `the database … is initialized; --rebuild only goes into a new, uninitialized database`: point 3 is incomplete. For any other message, follow the entries of Step 2.6. If the command failed after `/healthz` had begun to print `"keys":"uninitialized"`, continue with `npm run deploy -- --env production` without `--rebuild`.

5. Who: Agent. Fetch the backup:

   ```
   npx wrangler r2 object get clavifer-backups/<OBJECT_KEY> --remote --file work/production-restore.age --env production
   ```

   If `r2_buckets[0].bucket_name` of `env.production` is not `clavifer-backups`, use that name; the command the deploy entry printed already has it. Without `--remote`, wrangler reads its local simulation instead of the bucket. Verify: the command exits with status 0, and an existence check on `work/production-restore.age` prints `True`.

6. Who: Human. Send the message of point 3 of [Migrating to a new instance](#migrating-to-a-new-instance), with `work/production-restore.age` in place of the export and the private key of the backup recipient. The sealed records are in the same bucket, so the page should not report missing sealed files. If it reports 存储桶里缺少 … 个已封存的冷数据分段 (sealed files missing in the bucket), stop and ask the human to choose between 中止导入 (abort the import) and 不带这些分段继续 (continue without these files).

   Verify as in that point.

7. The hostname is unchanged, so the Passkeys come back with the backup. Every agent host logs in again: log in with every profile, as in the login step of [clients.md](clients.md), with the same `<SERVER>`. The client IDs stay the same.

The old database, if it still exists, stays as it is, and `work/production-restore.age` stays in the checkout. Deleting either is the human's decision.

### Resetting the Owner's password

When the Owner can no longer sign in, the operator of the deployment issues a recovery token. Resetting sets a new password and removes every Passkey and browser session of the Owner. Installations, grants and their logins stay. The token is valid for one hour.

1. Who: Agent. On the branch `deploy`, at the version that is running, run:

   ```
   npm run deploy -- --env production --issue-token
   ```

   The command deploys the checked-out code again, so it must not run with new code merged that is not meant to go live yet. Verify: the command exits with status 0, prints `Bootstrap token written to work/production-bootstrap.token; open /setup and enter it there.`, and ends with `https://<HOSTNAME> runs <version>.`

2. Who: Human. Say to the human:

   > 1. Open `work/production-bootstrap.token` in your own editor and copy its content. Do not paste it into this conversation. It is valid for one hour.
   > 2. Open `https://<HOSTNAME>/setup` in your browser, paste the token into 一次性令牌 (one-time token) and press 继续 (continue).
   > 3. The page shows 重置管理员登录 (reset the administrator's sign-in) and the email you sign in with. Enter 新密码 (new password, at least 12 characters), save it in your password manager, and press 重置密码 (reset password).
   > 4. Sign in with that email and the new password, and delete `work/production-bootstrap.token`.
   >
   > Tell me when you are signed in and the file is deleted.

   Verify: An existence check on `work/production-bootstrap.token` prints `False`. If the page reports that the token is wrong, expired or already used, repeat point 1.

3. Perform Step 3.2: the Passkeys are gone.

A snapshot taken before the reset carries the old password, so importing it brings the old password back.

## Server keys

The Worker has one secret, `ROOT_KEY`. The key that encrypts stored secrets and the secret Better Auth signs with are derived from it. It is a ring of `<id>:<32 bytes in base64url>` entries, the current one first; the deploy entry creates a ring with one key. When the Owner is created, the database records a fingerprint of every key in the ring. A Worker whose ring does not match the fingerprints answers `503 root_key_mismatch` on every route but `/healthz` and skips its scheduled work, so a replaced key cannot write data next to data it cannot read.

There is no procedure for rotating the key, and no copy of it exists. Never set, replace or delete `ROOT_KEY` by hand. A lost or overwritten key is recovered as described under [Recovering from a lost root key](#recovering-from-a-lost-root-key).

The values of individual stored secrets are a different matter: the Owner replaces them at any time on the 凭据 (secrets) page, with 轮换 / 编辑 (rotate / edit).
