# MCP

Use the connected service's discovered tools. Expected concepts are `credentials.list`, `access.request`, `access.status`, and `http.request`; use the host's actual namespace.

`credentials.list` returns the secrets granted to this installation and every connection. A connection carries `policy_json` (the allowed paths and methods, its regular scope, and the `deny` / `approval` / `free` rules: `METHOD /path`; `/*` covers sub-paths, `*` any method, `GET` also covers `HEAD`; plus `hosts`, the extra hosts a one-time invocation may name, each a hostname or `*.suffix` for every host below it, and `anyHost`, true when it may name any public HTTPS origin; absent means none), `description` (the Owner's usage notes, such as a non-secret header every request needs; follow them), `granted` (this installation holds a grant), `expires_at` (when that grant ends; `null` means until revoked; granted secrets carry it too) and `extensions` (its live temporary scope extensions). Paths containing a literal space, `;` or control / format characters are refused; `%2F` and `%20` inside a segment are accepted for keys that contain `/` or spaces. `http.request` accepts a configured connection and relative path and goes to the connection's own origin. It may name another `origin` only when the connection's `hosts` or `anyHost` cover that host, for example a download host the API points to, and then only after the Owner approved that exact invocation with the same `origin`; no grant, extension or free rule counts there. Do not copy raw secret values into model context.

Access flow for `http.request`:

1. Send the request directly first.
2. On an error, follow its `hint`:

| Error | Next step |
| --- | --- |
| `path_denied` | Stop. A deny rule (quoted in the hint) forbids it; only the Owner can lift it by editing the connection. Tell the user which rule; do not request access. |
| `path_not_allowed` / `method_not_allowed` | Outside the regular scope, not forbidden. One operation: `access.request` with `requested.invocation` set to this exact request. Multi-step work: `requested.grants` with a connection grant carrying `paths` and/or `methods` as a temporary scope extension. |
| `grant_required` | `requested.grants` for multi-step work, `requested.invocation` for one operation. |
| `approval_required` | `requested.invocation`; a grant or extension does not cover this request. A request that names an `origin` always ends here until that exact invocation, with the same `origin`, is approved. |
| `host_not_allowed` | The connection does not list the host of the `origin` you named. Tell the user which host is needed; the Owner can add it to the connection's extra hosts. Do not retry with another spelling of the address. |
| `invalid_path` | The hint names the refused character. Do not try other encodings; use an API that takes the key in the body (such as a bulk endpoint) or ask the user to do it manually. |
| `body_too_large` / `response_too_large` | Paginate or narrow the query, split writes, upload large files with the host's own tools. A too-large response means the request already ran. |
| `connection_not_found` | Tell the user which connection is needed: origin, authentication, suggested paths, methods and rules. If the user agrees, submit it as a draft with `access.request` `requested.setup` (credential field names only, with a test table); never submit one without asking. |
| `upstream_outcome_unknown` | The request may have run. Read the upstream state before deciding; never retry a write automatically. |
| `request_too_large` | The access request takes more than 256 KiB as stored, counted on its JSON after escaping. Split the draft into smaller requests or trim its tests, descriptions and body. |
| `too_many_pending` | This installation already has 20 requests, or 1 MiB of them as stored, waiting for the Owner (the hint says which). Tell the user and wait for the Owner to decide them; do not submit the request again until then, though a smaller one may still fit under the 1 MiB. |

   Write `reason` for the Owner: the target the way a person knows it (name, account, creation date), the expected effect, and for an opaque id how you identified it (for example "token ci-deploy created 2026-09-01, id from GET /user/tokens"), so the Owner can check it in the upstream console.
3. Wait for the Owner. Through the local `clavifer` bridge the `access.request` result carries `waitCommand`, a complete shell command (`clavifer --profile NAME status REQUEST_ID --wait`) that exits once the Owner decides and prints the final status JSON; in PowerShell prefix it with `& `. Claude Code: run it as a background command and end the turn; its exit wakes the session. Codex and other hosts without background notification: run it in the foreground, which blocks until the decision; set the host's command timeout no shorter than `--timeout`, or append a shorter `--timeout` and run it again after 124. `approved`: continue (resend the invocation, or start the granted work). For a grant request the status lists `grants` as they stand now, each with `expires_at` (`null` means until revoked; it can be later than the period just approved, because a re-grant only lengthens a grant) and `extensions` with their own `expiresAt`; tell the user how long the access lasts if it matters for the task. `denied` / `expired`: stop and tell the user. Exit code 124 means still pending after 25 minutes (`--timeout` changes it): run it again or ask the user. Without `waitCommand`, check `access.status` occasionally, never in a tight loop. After an invocation is `approved`, resend the identical request with `http.request` (same method, path, query, headers and body) within 10 minutes; it runs once, then `access.status` reports `executed`. A changed request is refused as unapproved. One-time approval works only through MCP: a REST client adds its own headers, so its request never matches. Sending the request uses the approval even when the upstream outcome is unknown; after `upstream_outcome_unknown`, check the upstream state before requesting again. Error results include a short `hint` naming the next step.

The recommended connection is local stdio: `clavifer --profile codex mcp` for the standard Codex installation, or `clavifer --profile claude mcp` for Claude Code. Login to the matching profile before connecting. The bridge refreshes tokens from the system credential store and sends only protocol messages on stdout. Claude Code normalizes dots in tool names to underscores, such as `mcp__clavifer__credentials_list`.

`http.request` arguments: `connection` (required resource ID), `path` (default `/`, no query string), `method` (default `GET`), optional string-to-string `query` and `headers`, optional UTF-8 string `body`, and optional `origin` (`https://host`, only for an approved invocation to one of the connection's extra hosts). Serialize JSON into `body` yourself and set `content-type` when needed. Tools/list publishes the exact input schemas. Responses are limited to 1 MiB; proxy requests time out after 20 seconds and never follow redirects or retry writes automatically.

`access.request` arguments: `{ "requested": { "grants": [{ "resourceType": "connection", "resourceId": "ID", "permission": "connection:invoke" }] }, "reason": "task purpose" }`. A connection grant may add `"paths": ["/v1/tokens"]` and/or `"methods": ["DELETE"]`, a temporary scope extension for requests outside the connection's allowed paths and methods (a list left out is fixed to the connection's current one when the Owner approves); it ends with the grant and deny and approval rules still apply. For raw local use the pair is `secret` / `secret:read`, and a secret grant accepts an optional `"fields": ["token"]` to request only part of the secret; omitting it requests every field. Approval never alters a grant the installation already holds, and a request whose fields differ from an active grant is rejected with `existing_grant_conflict`; ask the Owner to change it rather than resubmitting. A one-time request instead uses `{ "requested": { "invocation": { "connection": "ID", "method": "DELETE", "path": "/v1/items/7", "query": {}, "headers": {}, "body": "" } }, "reason": "why this exact call" }` (body at most 64 KiB); add `"origin": "https://files.vendor.example"` to send it to a host the connection's `hosts` or `anyHost` cover instead of its own origin, and resend it with the same `origin`. A draft of a new credential and the connections using it uses `{ "requested": { "setup": { "secret": { "name": "Vendor key", "fields": ["token"] }, "connections": [{ "name": "Vendor", "origin": "https://api.vendor.example", "paths": ["/v1"], "methods": ["GET"], "free": ["/v1/status"], "auth": { "type": "bearer", "field": "token" }, "tests": [{ "method": "GET", "path": "/v1/status", "expect": "run" }, { "method": "GET", "path": "/v1/items", "grant": true, "expect": "run" }] }] } }, "reason": "why this service" }`: the secret has field names only (the Owner enters the values once when approving), `connections` holds 1 to 20 connections that all use it (one entry per host when a key serves several), each taking what the Owner's form takes plus its own `tests` (it may list `hosts`, never `anyHost`, which only the Owner sets), with a name unique in the draft and an `auth` that names fields of that secret, never a `secretId`; connections without a credential all have auth `none` and the setup has no `secret`. A change to an existing connection uses `{ "requested": { "update": { "connection": "ID", "changes": { "deny": ["DELETE /v1/items/*"] }, "tests": [...] } } }`; `changes` takes `name`, `description`, `paths`, `methods`, `deny`, `approval`, `free`, never `origin` or `auth`. Each test is `{ "method", "path", "grant" (default false: no grant; true: a grant without extension), "expect" }` with `expect` either `run` or a refusal code; the server runs the tests on the draft policy at submission and refuses it with `tests_failed`, listing each mismatch (for a setup with the connection's index and name), so fix the draft or the expectation and submit again. Neither draft carries a grant. Once a setup is `approved`, `access.status` returns `connectionIds` in the order of `connections` (and `secretId`). A request holds exactly one of `grants`, `invocation`, `setup` or `update`. `access.status` takes `{ "id": "REQUEST_ID" }`; a request more than about 25 hours old may have been archived and then answers `request_not_found`.

An invoke-only grant never permits raw secret reads. The service does not inspect upstream responses for echoed credentials, so an upstream that reflects its own API key returns it to the caller; use only administrator-trusted API targets and never copy such a value onward. Metadata listing and request status are marked read-only; access requests and HTTP invocation can have side effects. Respect the host's tool approval rules.
